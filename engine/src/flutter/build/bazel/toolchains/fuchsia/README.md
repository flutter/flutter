# The Fuchsia toolchain: the rules_fuchsia spike (metric 0.7)

This directory holds the engine's end of the Fuchsia Bazel SDK, at the stage
of the Phase 0 spike: the rules (`@rules_fuchsia`) wired to the IDK and the
clang the checkout already has, a Python toolchain for the rules' tools, and
a test package built with them. Nothing here is part of the Linux host build;
every target is manual.

## What is wired, and where

- **The rules.** `MODULE.bazel` declares `rules_fuchsia` with an
  `archive_override` to CIPD's download of `fuchsia/development/rules_fuchsia`
  at the instance tagged with the IDK's git revision
  (`git_revision:1463df67e630ab75428ad5731ab1c24dd5dce1a9`, the tag on the
  `fuchsia/sdk/core/linux-amd64` instance DEPS pins). The integrity hash is
  the instance id's, so the download is verified and cached like any module.
  The two pins move together: an IDK roll in DEPS needs the rules instance
  carrying the new revision (`cipd describe fuchsia/sdk/core/linux-amd64
  -version <instance>` lists it).
- **The IDK.** `fuchsia_sdk_ext.local(path = "engine/src/third_party/fuchsia-sdk/sdk")`:
  `@fuchsia_sdk` is generated by the rules' repository rule over the 13 GB
  tree gclient syncs (the one GN's Fuchsia build reads), by symlink, not
  copy -- 519 IDK parts become 110 `pkg/` packages, the sysroots, the host
  tools (`ffx`, `cmc`, `far`, the FIDL compilers), in a few seconds.
- **Clang.** `fuchsia_clang_ext.local(local_path = "engine/src/flutter/buildtools/linux-x64/clang")`:
  `@fuchsia_clang` is the engine's clang (DEPS' `fuchsia/third_party/clang`,
  which is Fuchsia's own toolchain build and ships the Fuchsia target
  runtimes: `lib/x86_64-unknown-fuchsia`, `lib/aarch64-unknown-fuchsia`),
  so the clang pin is `clang_version` in DEPS by construction. The rules
  define the `cc_toolchain` for the Fuchsia platforms over it.
- **Python.** `../python:cpython3_toolchain`, a `py_runtime` over
  `@cpython3` (the CIPD CPython the engine's Python actions run), registered
  first in `MODULE.bazel` so that rules_python's hermetic toolchains -- which
  download an interpreter -- are never the ones resolved. The rules' tools
  are `py_binary`s; all of them run under `@cpython3` (116 of 116 Python
  invocations in the spike's action graph).
- **libc++.** `//engine/src/flutter/build/bazel/toolchains:cxx_runtime`, the
  from-source libc++ `.bazelrc` links into every binary, is now a `select()`
  that is empty outside Linux, Android, macOS and iOS -- GN's
  `use_flutter_cxx`. Fuchsia binaries take the toolchain's libc++ (the
  package carries `lib/libc++.so.2`, `libc++abi.so.1`, `libunwind.so.1`,
  `ld.so.1` from `@fuchsia_sdk//clang:libcxx_resources`), as GN's do.

## The spike

`spike/`: a gtest test (`fuchsia_cc_test`, three tests: compiled for Fuchsia,
the sysroot's libzircon links, the standard library) and its
`fuchsia_unittest_package`, API level 31 as GN's `fuchsia_target_api_level`.

    bazelisk build //engine/src/flutter/build/bazel/toolchains/fuchsia/spike:spike_test_package

produces `spike_test_package.far` (3.3 MB): `meta/spike_test.cm` from the
rules' generated manifest, `bin/spike_test` -- an x86-64 Fuchsia PIE linking
`libzircon.so`, `libfdio.so`, `libc++.so.2`, `libc++abi.so.1`, `libc.so` --
and the five runtime libraries, with `meta/fuchsia.abi/abi-revision`. The
rules' `fuchsia_package_tasks` also writes `spike_test_package.sh`, the
`bazel run` entry that publishes and runs the package on a device or
emulator through `ffx`, which is CI's half of the metric: this host has no
`/dev/kvm`, and the product bundles (`terminal.x64`) are downloaded only
with `run_fuchsia_emu` in DEPS.

**Bazel version.** The IDK's generated `BUILD.bazel` files declare the
prebuilt libraries as `cc_import(strip_include_prefix = "include")`, an
attribute Bazel 8.2.1's `cc_import` does not have (rules_cc 0.1.5 forwards
to the native rule on Bazel 8; rules_cc 0.2.x's Starlark `cc_import` is used
only on Bazel 9). Bazel 8.3.1's has it: the package analyzes and builds
under 8.3.1, 8.4.2 and 8.8.1 and not under 8.2.1. `.bazelversion` is 8.8.1
since 2026-10-20 (the user's call: the engine's pin moves ahead of Skia's
8.2.1, which only matters once Skia is consumed as a module, and then the
consumer's Bazel runs), so the spike builds with the pinned version.

## What the Fuchsia phase will have to decide

- Whose toolchain configuration: the rules' `cc_toolchain` compiles with
  the SDK's defaults (`-g3 -gdwarf-5 -gz=zstd -ftrivial-auto-var-init=pattern
  -Wthread-safety ...`, `--sysroot=arch/x64/sysroot`), GN's with the
  engine's (`-fstack-protector -fno-strict-aliasing -D_FORTIFY_SOURCE=2
  -Oz -flto ...`, `--sysroot=obj/x64-api-31/sysroot`, the API-level
  sysroot). Either the engine's copts come on top of the rules' toolchain,
  or the engine registers its own `cc_toolchain` for the Fuchsia platforms
  over the same clang and IDK sysroot and uses rules_fuchsia for the
  component and package rules alone.
- The module graph: `rules_fuchsia` brings `rules_python` (0.40.0 under
  MVS), and with it `protobuf`, `rules_java`, `rules_kotlin`,
  `rules_jvm_external`, `rules_android`, `abseil-cpp`, `googletest`, `re2`,
  `zlib` as *modules* (5 → 24). None is built or run by the Linux build,
  but `rules_java` and `protobuf` register toolchains, and Bazel loads every
  registered toolchain's package: every output base fetches their archives
  once (protobuf 94 MB, rules_kotlin 25 MB, rules_jvm_external 8.7 MB) and
  rules_java's `local_jdk` repository probes the host for a JDK. Skia's own
  module (rules_python 1.3.0, rules_go, rules_rust) brings a graph of this
  shape when it is consumed as a module; until then the spike could live
  in a module of its own under `spike/` instead (research/11, decision
  170).
- The sandbox's host tools: the rules' repository rule runs `find`, and the
  generated scripts begin `#!/usr/bin/env`; the engine's hermeticity check
  (tools/bazel_tools) will want an allowance or the rules a change.
