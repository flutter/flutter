# gn_to_bazel

Converts the engine's `BUILD.gn` files to `BUILD.bazel` files, for the
GN-to-Bazel migration. The GN files stay the source of truth while the two
builds coexist; the Bazel files are generated from them, and either checked in
(engine packages) or generated into an external repository when Bazel fetches
it (synced trees described by engine GN, such as Skia).

## Usage

```sh
cd engine/src/flutter/tools/gn_to_bazel
dart bin/gn_to_bazel.dart            # regenerate every checked-in file in the manifest
dart bin/gn_to_bazel.dart --check    # verify them (the presubmit)
dart bin/gn_to_bazel.dart ../../fml/BUILD.gn   # one file
dart test
```

The manifest (`lib/src/manifest.dart`) lists the GN files whose
`BUILD.bazel` is generated, each with the targets to skip (those whose
dependencies have no Bazel build yet, with the reason), Starlark to append
where the GN file has no way to say something Bazel needs, and labels every
compiled target must depend on (what GN leaves implicit, headers above all).
Adding a file to the migration means adding it there; the skip lists shrink as
it proceeds. `convertedFiles` are checked in and covered by `--check`;
`fetchTimeFiles` are generated by Bazel itself (below) and verified by the
build and the oracle.

Each input is written next to it as `BUILD.bazel` (or under `--out-dir`, laid
out by GN package). `--check` compares with the existing file instead and
fails on a difference. The output is piped through `buildifier` when one is
on `PATH` (or named by `--buildifier`; `--buildifier=none` for none); the
emitter already writes buildifier's format, so the result is the same either
way. `--depfile` writes the GN files read (the inputs and every imported
`.gni`), one per line. A run over the manifest also checks the hand-written
files that repeat a list of their GN file (`mirroredLists`: the Dart test
packages' `tests`, GN's `foreach` over it being what keeps those files
hand-written) against the GN assignment, and fails on a test the two do not
both name -- the one way a test added to GN's list could go missing here.

By default the converter assumes the Linux x64 host build: GN conditions on
`is_linux`, `is_win`, `enable_backtrace` and so on are decided the way GN
would decide them for that build, and the items they guard are emitted with
the condition as a comment. `--assume name=value` replaces the defaults;
`--assume=none` keeps every condition and renders it as a `select()`, which
needs a `config_setting` for each variable involved (see `conditionSettings`).
What the defaults leave open on purpose -- `is_debug`, the runtime mode,
`slimpeller` -- becomes a `select()` on the engine's config_settings. A
list config.gni computes from those (`feature_defines_list`, read by
reference in `//flutter/common:flutter_config`) is not evaluated: it is the
constant of `build/bazel/copts.bzl` that `referenceConstants` names
(`FLUTTER_FEATURE_DEFINES`, the same arithmetic over the flags), as the
Objective-C flag lists already are. A string around such a variable
(`"FLUTTER_ENGINE_VERSION=\"$engine_version\""` in `shell/version`)
renders as a concatenation with the constant -- here one of
`@engine_version//:version.bzl`, which a repository rule writes at fetch
time from git and DEPS, as `tools/gn` computes version.gni's arguments at
gen time. The oracle below reads the GN values from the out directory's
arguments (`gn args --list`).
Beneath any `--assume` sit the build's invariants (`buildInvariants`):
`is_clang = true`, which every configuration `tools/gn` writes has and the
clang-only Bazel toolchains cannot contradict, and `dart_src`, where DEPS
puts the Dart SDK and the Bazel wrap builds it from.

A `select()` holds a condition that is one setting, several joined by `||`,
or the negation of one or several (`!is_win`; `!is_win && !is_mac`, the
`else` of a chain), whose branch becomes the default. Conditions simplify
as they are built, using the one fact BUILDCONFIG.gn guarantees: the `is_*`
OS predicates (and the values one variable is compared with) are mutually
exclusive, so the path of `else if (is_mac)` after `if (is_ios)` is
`is_mac`, not `!is_ios && is_mac`. A conjunction of mixed settings
(`impeller_enable_opengles && !is_wasm`) keys a `config_setting_group`
generated into the file (`when_<condition>`, `match_all` over the terms'
settings), where a denied OS predicate is its complement group in
`//engine/src/flutter/build/bazel` (`not_wasm`: any of the other seven); a
denied flag has no complement and stays an error.

A scalar (`metal_version`, `testonly`) may be assigned under conditions,
including reassigned: its cases -- each value with the condition under
which it is the last one written -- render as a `select()` on the
attribute, with `None` where GN leaves the variable undefined. A boolean
written that way is read back as one formula. A list may only be appended
to in a branch, and a target's name cannot vary at all (`output_name` under
`is_win`).

A GN argument whose default GN derives from the platform -- Impeller's
`impeller_enable_{metal,opengles,vulkan}`, and `enable_unittests` -- is a
Bazel flag or setting (`impeller/tools/BUILD.bazel`, `//flutter/testing`'s
appendix), named in `conditionSettings` and `knownExternalVariables`. In a
`declare_args()` block such an argument keeps its name instead of its
default's formula (Bazel sets the per-platform value in configuration);
arguments derived from it (`impeller_enable_compute = vulkan || metal`)
stay formulas over the settings. The host assumptions fix them as `tools/gn`
would.

A target GN defines only under a condition exists in Bazel with
`target_compatible_with` incompatible wherever the condition fails, on every
rule the target produced (the `impeller_shaders` macro forwards it to each
target it creates). GN's placeholder idiom -- `if (c) { real(name) } else {
group(name) {} }`, an empty group so that dependents can name the target
unconditionally -- drops the group; any other duplicate name is an error.

### Fetch-time conversion

```sh
dart bin/gn_to_bazel.dart --out-dir=<repo> --repository=@skia=//flutter/third_party/skia \
    --depfile=<repo>/gn_to_bazel.d --buildifier=none \
    ../../skia/BUILD.gn ../../skia/modules/skcms/BUILD.gn ...
```

`--repository=@name=//gn/dir` lays the inputs out as the packages of an
external repository whose root is that GN directory: files under it are
written relative to it, labels into other packages of the repository as
`//pkg:file`, and anything outside the repository is an error. The
repository rule `synced_repository` in `build/bazel/repositories.bzl` runs
exactly this during fetch (with the checkout's own Dart SDK and `gn`), then
watches every file in the depfile and the converter's sources, so a roll of
the synced tree or an edit to the GN re-converts on the next build. Labels
into the main repository are written through its module name
(`@flutter//engine/src/...`), which is how an extension-generated repository
sees it.

### The oracle

```sh
dart tool/gn_desc_diff.dart --out=out/host_debug_unopt --assume=is_debug=true ../../skia/BUILD.gn
```

compares the converter's reading of each target -- type, sources, public
headers, dependencies, public configs, and the defines and include
directories of configs -- with `gn desc` of a real GN out directory. Run it on
every new conversion: the generated file is right when the oracle agrees and
Bazel builds it.

### Compile-command parity

```sh
(cd ../.. && ./flutter/third_party/gn/gn gen out/host_debug_unopt --export-compile-commands)
bazel aquery --output=jsonproto -c dbg \
    'mnemonic("CppCompile", deps(//engine/src/flutter/display_list:display_list_unittests))' \
    > /tmp/aquery.json
python3 tool/compile_command_diff.py --aquery=/tmp/aquery.json \
    --compile-commands=../../out/host_debug_unopt/compile_commands.json --engine-only
```

checks the other end: for every source file both systems compile, the flags of
the two compiler invocations, normalized (paths engine-relative, outputs and
depfiles dropped, each build system's own include mechanics ignored, the exec
configuration left out). The accepted differences are a dependency's public
defines reaching transitive dependents in Bazel where GN stops them after a
private edge (`U_STATIC_IMPLEMENTATION`, `XML_STATIC`, `SK_SHAPER_*`; GN's
`deps` and `public_deps` both become `deps`, see "How it works"), GN's `-I` for
directories Bazel serves through `include_prefix`, and GN carrying a shader
*tool*'s `all_dependent_configs` into `impeller/renderer`. Anything else is a
converter gap or a GN oddity worth a look; `--full` lists every class.

## How it works

GN build files are programs; Bazel wants data. The converter has three layers:

1. `gn_ast.dart` -- the syntax tree, read from `gn format --dump-tree=json`.
   GN's own parser is the only parser. `GnSourceTree` resolves `//` paths and
   loads files on demand (for imports), remembering them for the depfile. It
   reads `secondary_source` from `.gn`: a `BUILD.gn` under
   `//flutter/build/secondary/X` stands in for `//X` (its GN directory,
   relative paths and imports resolve as if it were there), and a `.gni` is
   found there when the primary tree lacks it -- the engine describes
   libwebp, wuffs and expat that way.
2. `gn_eval.dart` -- a symbolic evaluator. Each assignment is recorded with
   the condition under which it happens, so `if (is_linux) { sources += [...] }`
   becomes "under `is_linux`, append these to `sources`". Assumptions fix
   variables and prune dead branches. `import()` evaluates the imported
   `.gni` in its own scope and merges its variables and templates (names
   starting with `_` stay private, as in GN) -- for the files the import
   policy names; the engine's own configuration files are "known" instead,
   their variables listed in the mapping tables. `declare_args()` defaults
   yield to the assumptions, which play the role of `args.gn`. A
   `template()` is a closure over its defining scope; an invocation evaluates
   the caller's block into `invoker` and runs the body with `target_name`, so
   the targets it defines are ordinary targets (the first one named
   `target_name` takes the invocation's comments). `forward_variables_from`,
   `target(type, name)`, scope values (`x.member`, `defined(x.member)`),
   `get_path_info(p, "abspath")` (of a path or a list of them), short-circuit `&&`/`||` and integer
   comparisons are understood; `rebase_path()` and `exec_script()` yield
   opaque values that are an error only if they reach the output. `+=` and
   `-=` on a variable of an enclosing scope (a template body appending to a
   forwarded `public_configs`) modify a copy in the current scope and leave
   the enclosing variable alone, as GN does; a `config`'s `_`-prefixed
   variables are its locals and carry nothing.
3. `starlark_emitter.dart` -- the mapping from GN targets to Bazel rules:
   `source_set`/`static_library` to `cc_library` (with headers in `hdrs`, or
   the `public` list when there is one; a `source_set` is `alwayslink`,
   since GN links all of its objects), `group` to a `cc_library` of only
   `deps`, test executables to `cc_test`, `shared_library` to a
   `cc_binary(linkshared = True)` named after the file GN produces
   (`lib<output_name>.so`, which Bazel requires of a shared binary) with an
   `alias` under the GN name, the C++ runtime in its `deps` (GN's default
   deps; Bazel's `link_extra_libs` reaches executables only) and any
   `cc_library` of the same file that would declare the same `.so` made
   `linkstatic`, `config` to a header-only
   `cc_library` carrying the defines, include directories and link flags that
   dependents list in `deps`, known `.gni` templates to the matching Bazel
   macros. GN's `deps` and `public_deps` both become `deps`: GN's include
   paths make every header of every transitive dependency visible, private
   or not, and `gn check` follows only the first edge, so a header that
   includes a private dependency's header is normal in the engine
   (`impeller/geometry/point.h` includes `fml/logging.h`); a sandboxed
   compile sees declared inputs alone, and `implementation_deps` would
   withhold exactly those. What a private GN dependency withholds from
   dependents is its public configs' defines; what dependents gain from the
   mapping shows up as extra defines when Bazel's compile commands
   (`bazel aquery`) are set against GN's `compile_commands.json`. Every
   compiled target also depends on `//engine/src:include_root`, GN's
   `default_include_dirs` (`-I//`). A private config of the same file is
   inlined instead (its defines as `local_defines`, its flags as `copts`),
   since a dependency's `defines` would leak to dependents where GN's
   private configs never do; a header-only target drops their defines and
   flags, as GN applies them to no compile, and keeps their link flags
   (`libs`, `ldflags`: inlined, or carried by the config's library as an
   `implementation_deps` entry), which GN hands to every link that reaches
   the target whether or not it compiles. The configs a target inherits through its
   dependencies' `all_dependent_configs` become public `deps` of the
   target, so that Skia's `SK_VULKAN` and friends reach the engine as they
   do under GN. A public config's compiler flags cannot ride a dependency:
   they are inlined into the owner, and a dependent gets them on its own
   `copts` from the dependency's GN file (`forwarded_flags.dart` evaluates
   it under the run's assumptions, once, and reads the target's public
   configs and, recursively, what its `public_deps` hand on, as GN forwards
   public configs along `public_deps` chains -- wuffs's suppressions reach
   whoever includes it, the Vulkan allocator's everything on
   `//flutter/impeller`'s public side, gmock's
   `-Wno-inconsistent-missing-override` every test through
   `//flutter/testing:testing_core`); a flag handed on under a condition (a
   `public_deps` entry inside an `if`) lands in a `select()`, and the
   owner's conversion checks that its own reading of its public configs is
   what its dependents will derive. A dependency whose file the converter
   cannot evaluate (the Dart runtime's, abseil's) hands nothing it can see;
   the compile-command parity check is the backstop. A
   private config of another file (`configs += [ "../../:skia_private" ]`)
   is an `implementation_deps` entry: Bazel applies it to the target's own
   compiles alone, which is GN's private semantics. A file of another
   package of the main repository (a font under `//flutter/txt` as a
   fixture) is labelled through that package, which the manifest-derived
   `mainRepositoryLayout` knows; an unknown owner is an error.
   `cflags_c` and `cflags_cc` go to `conlyopts` and `cxxopts`; a `-std=` in a
   target's flags is dropped, because GN's compiler config sets the standard
   after every target's flags and the target's never takes effect. Bazel
   reads `defines`, `copts` and `linkopts` with Make-variable substitution
   and shell tokenization where GN hands the compiler each string as it is,
   so those strings are escaped to survive the reading (`X="v"` is written
   `X=\"v\"`; `$` is doubled). A define that embeds a generated file's GN
   path (`get_label_info(..., "target_gen_dir") + "/x.bin"`) is written
   with the file's run-time path relative to the source root, which is what
   a test joins to `GetSourcePath()`, and the file must reach the test as
   `data` (`testRuns`); an `ldflags` entry naming a source file through
   `rebase_path(..., root_build_dir)` (the embedder's version script) becomes
   `$(execpath :file)` with the file in `additional_linker_inputs`. A file
   listed twice is emitted once. Every compiled target gets `FLUTTER_COPTS`
   (engine code: it lists `//flutter:config` or depends on engine code),
   `CHROMIUM_CODE_COPTS` (the third-party trees the engine describes with
   GN, such as Skia) or `FLUTTER_THIRD_PARTY_COPTS` (`no_chromium_code`),
   from `build/bazel/copts.bzl`; a target's own `cflags` come *before*
   that constant, as they come before every config's flags on GN's command
   line (lib/ui's `-Wimplicit-float-conversion` is followed, and partly
   undone, by `default_warning_flags`). `action()` becomes a `gn_action`
   (`build/bazel/gn_action`): GN's build-directory variables evaluate to
   paths under `//@gen` and `//@out`, `rebase_path(x, root_build_dir)`
   becomes a marked path that only an action's `args` may carry, and the
   emitter writes it as the rule's token -- `$(execpath label)` for a source
   file (declared as an input if GN did not), `$(src dir)` for a source
   directory, `$(gen path)` for anything generated; outputs must be under
   `$target_gen_dir`. A dependency on an action of the same file becomes a
   source of the dependent, since the outputs are inputs of its compile in
   Bazel where GN only ordered the two; one on a `copy()` of the same file,
   or on a target of a template whose macro produces files rather than a
   library (`TemplateMapping.files`: `dart_snapshot_aot`,
   `dart_snapshot_kernel`, `impellerc`), becomes `data`, since the dependent
   reads the product at run time (the GTK shell's suite and its compiled
   GSettings schemas; `//flutter/testing:fixture_test` and the VM service's
   AOT snapshot in the profile mode). A generated directory in
   `include_dirs` is the package's, as Bazel's `includes` spans the output
   tree; an ancestor package's (`$root_gen_dir/flutter`) is a dependency on
   the target whose `includes` already name that directory
   (`genDirIncludeTargets`); an include directory in another repository, or
   in another package of this one, is a dependency on the library that
   carries it when `includeDirLibraries` names one (ANGLE's `include/`; the
   core client wrapper's `include/flutter`, a library its manifest appendix
   adds, since Bazel's `includes` is package-relative), and is otherwise
   dropped with a note (the dependency on that repository carries it, or
   nothing does). A config another file computes with `exec_script()`
   (`//flutter/shell/platform/linux/config`'s `pkg_config()` answers) is
   hand-written and named in `configEffects` like any other. `copy()` becomes a `gn_copy`, whose content is its
   sources; GN's destination under the build directory is recorded, not
   reproduced -- unless the outputs are under the copy's own
   `target_gen_dir` and name the files, literally (a renaming copy) or
   through `{{source_file_part}}`/`{{source_name_part}}` with more than the
   bare name around them (`assets/{{source_name_part}}/gschemas.compiled`),
   when the copies are produced under those names (`outs`), expanded per
   source as GN expands them. A known template's invocation becomes the macro call its
   `TemplateMapping` describes, argument by argument: files of the package,
   labels, configs (which become the labels of their config libraries) or a
   scalar; the template's body is the macro's (`flatbuffers()` in
   `build/bazel/flatbuffers`), and the targets it expands to in GN are the
   mapping's `innerTargets`, which the oracle expects.

`bazel_mapping.dart` holds the converter's knowledge of the engine: label
translations for synced dependencies (`//flutter/third_party/icu` is `@icu`,
`//flutter/skia` is `@skia`), what each GN config contributes, which
`config_setting` stands for which GN predicate, the import policy, the
test sizes, how `testing/run_tests.py` runs a suite (`testRuns`: the
arguments it passes `flow_unittests` -- the goldens directory and the font --
become the test's `args` and `data`, the environment it sets the
GTK shell's suite -- `G_DEBUG=fatal-criticals` -- its `env`, and the
options it gives gtest-parallel for `ui_unittests` -- `--timeout=90` -- its
`runner_args`, since GN's executable has no words for how it is run;
`gtestParallelSuites` names the suites `run_tests.py` puts through
gtest-parallel, a process per test and every test twice, which become
`flutter_cc_test` rather than `cc_test`; `benchmarkRuns` names the
benchmark executables `run_tests.py --type benchmarks` runs with ICU's data
file, which become `cc_test`s tagged `benchmark` and `manual` -- out of a
wildcard run, as every CI builder but `host_release_test` leaves them, and
under `//engine/src/flutter:benchmarks` -- where GN's other testonly
executables stay binaries; `displayTests` and
`sessionBusTests` name the suites that need a display and a D-Bus session
bus, which the run inherited from the bot), and which executables need the GPU test backends next
to them (`gpuBackendTests`: suites, and `flutter_tester_opengles`, an
ordinary executable that the Dart suites run and that carries them as
runfiles). An executable whose `output_name` is its own name converts (the
file Bazel produces anyway); one that renames its output does not yet.
Extending the converter's coverage means adding to these tables.

### Strict mode

The converter never guesses. Anything outside the subset it understands --
`foreach`, string expansions of unknown variables, an unknown import, a label
with no Bazel home, a config with no mapping, a condition with no
`config_setting`, a file outside the output repository -- is an error that
names the GN file and line. The fix is either to teach the converter the
construct or to simplify the GN file; GN build files that are plain data
convert cleanly.

### Comments

Comments travel with what they document: a comment above a target precedes
the rule, a comment above a `=` precedes the attribute, a comment above a
`+=` or above a list item stays with the item. Comment blocks that stand on
their own (separated by a blank line) are left behind.
